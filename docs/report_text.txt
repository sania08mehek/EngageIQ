Chapter 1
INTRODUCTION
The shift towards remote and hybrid working has made physical presence an unreliable measure of employee productivity, engagement, and collaboration. Traditional monitoring methods, such as keystroke tracking, screenshots, and webcam surveillance, can also raise concerns about privacy, personal autonomy, and workplace trust.
EngageIQ addresses these challenges through a dual-layer approach that considers both work patterns and actual work outcomes.
Signal Layer: Examines work patterns using indicators such as meeting load, focus-time gaps, response delays, and after-hours activity.
Output Layer: Measures actual work delivery through task completion, sprint velocity, deadline adherence, code commits, pull requests, self-reported effort, and rework.
Both layers are combined through the PACE (Productivity Assessment and Context Evaluation) framework, which assigns 40% weightage to EHS and 60% to OPI.
Rather than making automated employee decisions, EngageIQ identifies trends, unusual patterns, and potential risks for further review. Its Human-in-the-Loop (HITL) approach follows a structured process:
Collect → Normalise → Measure → Score → Detect Trends → Flag Risk → Human Review
This approach promotes data-driven and transparent workplace assessments, ensuring that insights support human judgement instead of relying solely on employee monitoring or individual performance metrics.
1.1Background 
Remote and hybrid work have made it difficult for organisations to assess employee productivity based on physical presence alone. EngageIQ addresses this gap by focusing on work patterns and actual work outcomes through two layers: the Signal Layer and the Output Layer.
The Signal Layer uses approved work-related metadata from platforms such as Google Calendar, Microsoft Outlook, Slack, and Microsoft Teams. The Output Layer collects delivery-related information from tools such as Jira, Asana, GitHub, and GitLab to assess task progress and completion.
The system follows a data-minimisation approach, collecting only the information required for the approved productivity metrics. Its design also draws on the SPACE framework, which recognises that productivity involves multiple dimensions rather than a single activity or measurement.

 Proposed approach

It processes the collected information and extracts relevant features to calculate two key measures: Employee Health Score (EHS) and Output Performance Index (OPI).

2.1 Multidimensional Productivity Measurement
Forsgren et al. proposed the SPACE framework, which highlights that developer productivity involves multiple dimensions and cannot be accurately evaluated using just one activity-based measure [1]. This idea forms the basis of EngageIQ's dual-layer approach, where work-pattern health and actual work output are evaluated separately to provide a more balanced understanding of employee productivity.
2.1.1 Relevance to EngageIQ
EngageIQ adopts this multidimensional approach through two complementary measures: EHS (Employee Health Score) and OPI (Output Performance Index). EHS focuses on employees' work patterns and overall work-pattern health, while OPI evaluates their actual work delivery and outcomes. Both indicators are brought together through the PACE framework, providing a more comprehensive view of workplace productivity.
2.2 People Analytics and Employee Prediction
Polzer discusses the increasing importance of people analytics in helping organisations understand workforce trends, identify internal patterns, and make better-informed decisions [3]. However, the value of these insights largely depends on the quality of the data, how accurately the results are interpreted, and the presence of responsible data governance practices.
2.2.1 Machine Learning for Employee Prediction
Talebi et al. examined various machine learning techniques for predicting employee turnover, highlighting how these methods can be applied to workforce-related analysis [2]. Their study also points out the importance of selecting suitable models and maintaining good data quality to achieve reliable results. Building on a similar analytical approach, EngageIQ incorporates data analytics and machine learning techniques within an explainable framework, where the generated insights are further examined through human review rather than being treated as final decisions.
2.3 Burnout and Work-Pattern Analytics
Liu et al. introduced HiPAL, a deep-learning-based framework that uses activity logs to predict potential burnout among employees [4]. In contrast, EngageIQ takes a different approach by concentrating on changes in work patterns and productivity indicators rather than attempting to predict or diagnose burnout. Any unusual patterns identified by the system are treated as potential warning signals and are referred for human review, ensuring that the results are not interpreted as medical conclusions.
2.3.1 Responsible Interpretation
The World Health Organization (WHO) recognises burnout as an occupational phenomenon rather than a medical condition [8]. Keeping this distinction in mind, EngageIQ does not attempt to diagnose burnout. Instead, it identifies work-related patterns that may indicate a need for further attention, with all such observations subject to a Human-in-the-Loop (HITL) review process before any conclusions are drawn.

3.4 EHS Algorithm
The Employee Health Score (EHS) evaluates employees' work-pattern health on a scale of 0 to 1, where higher scores indicate healthier work patterns.
It uses a weighted formula that considers meeting load, focus-time gaps, response delays, and after-hours activity:
 EHS = 1 - (0.30n_{meeting} + 0.30n_{focus} + 0.20n_{response} + 0.20n_{afterhr})
The final score is restricted to the [0, 1] range. Under this normalisation method, lower values across these four indicators contribute to a higher EHS score. The calculation has a time complexity of O(n), as it processes the relevant events in a single pass.
3.5 OPI Algorithm
OPI (Output Productivity Index) measures tangible work delivery on a 0–1 scale using task completion, sprint velocity, deadline adherence, code activity, and rework.
Key measures include:
Completion rate = completed tasks / total tasks 
Velocity = completed story points 
Deadline adherence = on-time tasks / completed tasks 
Code activity = commits + pull requests 
Rework ratio = reopened or revised tasks / total tasks 
The documented weighting begins with 0.25 for completion rate and 0.25 for velocity, with the remaining weights assigned to deadline adherence, code activity, and rework as defined in the project algorithm.
3.6 PACE Fusion

                                  Figure 3.2: PACE Dual-Lens Scoring Model
The PACE score combines EHS and OPI using the defined weights:
PACE = (0.4 × EHS) + (0.6 × OPI)
For example, if EHS = 0.50 and OPI = 0.80, then PACE = 0.68. OPI receives a higher weight to emphasize tangible work output over communication or activity levels.
3.7 Trend and Anomaly Detection
EngageIQ identifies potential risks by analysing changes over time rather than relying on a single score. The MVP uses the previous six periods to calculate a rolling mean and standard deviation. Any deviation exceeding 1.5 standard deviations is flagged as an anomaly.The rolling-window calculation has a time complexity of O(window) per employee. More advanced techniques, such as LSTM-based models, may be introduced in the future when sufficient historical data is available.

For our databases, we use SQLite for quick demos and step up to PostgreSQL for the live production environment. 6.2 Implementation Modules
6.2.1 Data Ingestion
The ingestion module acts as the entry point for our data, pulling information from various systems using connectors or simple CSV files. It handles all the behind-the-scenes housekeeping—logging in securely, grabbing data on a schedule, and only pulling in what's new so we don't waste time. It also double-checks that the data coming in makes sense, automatically tries again if a connection drops, manages speed limits so we don't overwhelm the system, and makes sure all the timestamps line up perfectly.
6.2.2 Data Processing and Feature Engineering
The processing module takes all that raw data and cleans it up so it's actually usable. It strips out any useless information, makes sure all the dates and times match up, and smoothly handles any missing blank spots. From there, it groups everything together by employee and timeframe, getting the information perfectly organized and ready for the EHS and OPI systems to take over.
6.2.3 EHS and OPI Engines
The scoring system calculates everything using our set formulas. It doesn't just spit out a final score, though—it also outputs the specific metrics used to get there. Providing those underlying numbers is intentional, as it allows the dashboard to clearly break down exactly why someone's score went up or down.
6.2.4 Dashboard and Reporting
According to the documentation, the dashboard can be built using either Streamlit or a combination of React and Recharts [12].  The design focuses on looking at the data from different angles—offering views for the whole organization, specific teams, and individual employees. Instead of just slapping a single rank or score on an employee, the setup is meant to show the bigger picture by highlighting trends, data breakdowns, past review histories, and the context behind the numbers.
6.2.5 Alerts and Notifications
The alert system is designed to notify the right people only when there's a genuine issue or a significant change. We've set it up to send these alerts right inside the app or straight to your email. To keep things from getting annoying, the system allows you to set custom limits, ensuring people aren't spammed with notifications over every tiny blip in the numbers.

Chapter 8
SOCIAL, LEGAL, ETHICAL, SUSTAINABILITY AND SAFETY ASPECTS
Since EngageIQ handles real workplace data, we can't just focus on the tech—we have to carefully consider the legal, ethical, and social sides of things too. The core idea here is to help companies understand how their teams are doing in a healthy, responsible way. It is absolutely not meant to be a creepy surveillance tool or a system that blindly grades or penalizes employees on its own.
8.1 Social and Ethical Considerations
The whole point of EngageIQ is to move away from just tracking who stays online the longest. Instead, it looks at healthy work habits right alongside what is actually getting done. Just keep in mind that these numbers are meant to be a helpful guide to look at the big picture, not the absolute final word on how someone is performing.
8.1.1 Fairness and Role Awareness
Since every job looks a bit different, it doesn't make sense to measure a software developer the exact same way you'd measure someone in sales. Because of this, EngageIQ sets expectations based on the specific role, rather than trying to force a single, one-size-fits-all standard on the entire company.
8.1.2 Human Agency
The alerts the system flags are just meant to be a heads-up for a real person to review, not a definitive diagnosis of a problem. Managers need to look at the full context before making any decisions. Most importantly, the system should never be used to automatically punish or fire someone just because of a dip in their numbers.

8.3 Legal and Compliance Considerations
A production deployment would need to comply with the data-protection, employment, information-security, contractual, and organizational policies applicable to the deployment jurisdiction. We didn't write this report based on one specific set of laws, mostly because companies might use the system all over the world. 8.4 Sustainability
EngageIQ supports responsible digital-work infrastructure and aligns with SDG 3, SDG 8, and SDG 9. Its MVP uses batch-based statistical processing, while more computationally intensive methods such as LSTM are reserved for cases where sufficient data justifies their use.
8.5 Safety and Responsible Use
EngageIQ isn't meant to act as a doctor, and it definitely shouldn't be making hiring or firing decisions on its own. The dashboards are designed to show the bigger picture and how things are trending over time, rather than just slapping a simple grade on someone's performance. Any alerts that pop up should always be looked at by a real person who can double-check the information and ultimately make the final call themselves.

Chapter 9
CONCLUSION
EngageIQ is a thoughtful system designed to understand how remote teams are doing by looking at two main things: healthy work habits and actual results. It basically looks at the data from two different angles. First, it measures employee health and well-being (EHS), and second, it measures the actual work being produced (OPI). We bring these two sides together using our PACE formula. By putting 40% of the focus on well-being and 60% on actual output, we make sure we are valuing the real work getting done over just how often someone is sending emails or chatting online.
9.1 Conclusion
The whole goal of this project is to figure out how teams are doing without being creepy or breaking their trust. We do this by looking at basic work information and combining it into our EHS, OPI, and overall PACE scores, while always making sure a real person is reviewing the final results. While the math behind it is clear and solid, it's still just a prototype right now—definitely not something ready to be used for actual hiring or firing choices. Before we can confidently roll this out in the real world, we need to do a lot more testing to make sure we are balancing and measuring everything fairly.

    response_latency,
    after_hours_ratio
):
    meeting_weight = 0.30
    focus_weight = 0.30
    response_weight = 0.20
    after_hours_weight = 0.20
    weighted_load =
          (meeting_weight * meeting_load)
        + (focus_weight * focus_gap)
        + (response_weight * response_latency)
        + (after_hours_weight * after_hours_ratio)
    EHS = 1 - weighted_load
    // Restrict the score to the valid range [0, 1]
    EHS = maximum(0, minimum(1, EHS))
    RETURN round(EHS, 4)
END FUNCTION





A.2 OPI Computation
FUNCTION compute_OPI(
    completion_rate,
    velocity,
    deadline_adherence,
    code_activity,
    rework_ratio
):
    completion_weight = 0.25
    velocity_weight = 0.25
    deadline_weight = 0.20
    activity_weight = 0.20
    rework_weight = 0.10
    positive_delivery =
          (completion_weight * completion_rate)
        + (velocity_weight * velocity)
        + (deadline_weight * deadline_adherence)
        + (activity_weight * code_activity)
    rework_penalty = rework_weight * rework_ratio
    OPI = positive_delivery - rework_penalty
    // Restrict the score to the valid range [0, 1]
    OPI = maximum(0, minimum(1, OPI))
    RETURN round(OPI, 4)
END FUNCTION



A.3 PACE and Risk Classification
FUNCTION compute_PACE(EHS, OPI):
    EHS_weight = 0.40
    OPI_weight = 0.60
    PACE =
          (EHS_weight * EHS)
        + (OPI_weight * OPI)
    PACE = maximum(0, minimum(1, PACE))
    RETURN round(PACE, 4)
END FUNCTION

FUNCTION classify_risk(PACE, persistent_anomaly = FALSE):
    IF PACE >= 0.70 THEN risk_band = "Healthy"
    ELSE IF PACE >= 0.40 THEN risk_band = "Moderate"
    ELSE
        risk_band = "At-Risk"
    END IF
    // The current pipeline does not calculate trend anomalies and therefore normally uses persistent_anomaly = FALSE.
    IF persistent_anomaly == TRUE AND risk_band != "At-Risk" THEN
        IF risk_band == "Healthy" THEN risk_band = "Moderate"
        ELSE IF risk_band == "Moderate" THEN risk_band = "At-Risk"
        END IF
    END IF
    RETURN risk_band
END FUNCTION
