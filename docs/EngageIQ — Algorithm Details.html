EngageIQ (PACE) — Algorithm Details

Core algorithms behind the PACE scoring engine: EHS computation, OPI computation, PACE score fusion, trend/anomaly detection, and risk classification.

1. End-to-End Pipeline

flowchart TD
    A[Raw data: Calendar, Slack/Teams, Jira, GitHub] --> B[Ingestion & Normalization]
    B --> C[Feature Engineering]
    C --> D1[EHS Algorithm]
    C --> D2[OPI Algorithm]
    D1 --> E[PACE Fusion: 0.4·EHS + 0.6·OPI]
    D2 --> E
    E --> F[Trend & Anomaly Detection]
    F --> G[Risk Classification]
    G --> H[Dashboard / Alerts]
    H --> I[Human-in-the-Loop Review]

2. EHS Algorithm (Engagement / Work-Pattern Health Index)

Goal: score the health of an employee's work pattern from calendar/communication metadata, in the range [0, 1], where higher = healthier.

Flowchart

flowchart TD
    A[Calendar + chat metadata for period] --> B[Compute meeting_load]
    B --> C[Compute focus_gap]
    C --> D[Compute response_latency]
    D --> E[Compute after_hours_ratio]
    E --> F[Normalize each feature to 0-1 vs baseline]
    F --> G[Weighted sum of normalized features]
    G --> H[Clip to 0-1 range]
    H --> I[Return EHS]

Pseudocode

FUNCTION compute_EHS(employee_id, period):
    events   = get_calendar_events(employee_id, period)
    messages = get_comm_metadata(employee_id, period)

    meeting_load   = total_meeting_hours(events) / period.working_hours
    focus_gap      = 1 - (longest_uninterrupted_block(events) / period.working_hours)
    response_lat   = avg_response_time(messages)
    after_hours    = count_events_outside(events, work_start, work_end) / total_events(events)

    // normalize each raw feature against the employee's rolling baseline
    n_meeting  = normalize(meeting_load,  baseline.meeting_load,  clip=[0,1])
    n_focus    = normalize(focus_gap,     baseline.focus_gap,     clip=[0,1])
    n_response = normalize(response_lat,  baseline.response_lat,  clip=[0,1])
    n_afterhr  = normalize(after_hours,   baseline.after_hours,   clip=[0,1])

    // lower meeting_load, focus_gap, response_lat, after_hours => healthier
    W1, W2, W3, W4 = 0.30, 0.30, 0.20, 0.20   // configurable weights, sum = 1

    EHS = 1 - (W1*n_meeting + W2*n_focus + W3*n_response + W4*n_afterhr)
    EHS = clip(EHS, 0, 1)

    RETURN EHS, {meeting_load, focus_gap, response_lat, after_hours}  // score + explainability
END FUNCTION

Complexity: O(n) over calendar/chat events in the period — one pass to aggregate, constant-time normalization and fusion.

3. OPI Algorithm (Output Productivity Index)

Goal: score actual delivery output from Jira/GitHub metadata, range [0, 1], higher = more productive.

Flowchart

flowchart TD
    A[Jira + GitHub metadata for period] --> B[Compute task_completion_rate]
    B --> C[Compute sprint_velocity]
    C --> D[Compute deadline_adherence]
    D --> E[Compute code_activity: commits + PRs]
    E --> F[Compute rework_ratio]
    F --> G[Normalize vs role baseline]
    G --> H[Weighted sum]
    H --> I[Return OPI]

Pseudocode

FUNCTION compute_OPI(employee_id, period, role):
    tasks   = get_jira_tasks(employee_id, period)
    commits = get_git_activity(employee_id, period)

    completion_rate  = count(tasks.status == DONE) / count(tasks)
    velocity         = sum(tasks.story_points WHERE status == DONE)
    deadline_adhere  = count(tasks.completed_on_time) / count(tasks.completed)
    code_activity    = commits.count + prs.count
    rework_ratio     = count(tasks.reopened OR tasks.revised) / count(tasks)

    // role-aware normalization: engineer vs sales vs design use different baselines
    baseline = get_role_baseline(role)
    n_completion = normalize(completion_rate, baseline.completion, clip=[0,1])
    n_velocity   = normalize(velocity,         baseline.velocity,   clip=[0,1])
    n_deadline   = normalize(deadline_adhere,  baseline.deadline,   clip=[0,1])
    n_code       = normalize(code_activity,    baseline.code,       clip=[0,1])
    n_rework     = normalize(rework_ratio,     baseline.rework,     clip=[0,1])   // higher rework is worse

    W1, W2, W3, W4, W5 = 0.25, 0.25, 0.20, 0.20, 0.10   // sum = 1

    OPI = W1*n_completion + W2*n_velocity + W3*n_deadline + W4*n_code - W5*n_rework
    OPI = clip(OPI, 0, 1)

    RETURN OPI, {completion_rate, velocity, deadline_adhere, code_activity, rework_ratio}
END FUNCTION

Complexity: O(n) over tasks + commits in the period.

4. PACE Fusion Algorithm

Flowchart

flowchart LR
    A[EHS score] --> C[PACE = 0.4·EHS + 0.6·OPI]
    B[OPI score] --> C
    C --> D[Store PACE with timestamp]
    D --> E[Append to employee history]

Pseudocode

FUNCTION compute_PACE(EHS, OPI):
    PACE = (0.4 * EHS) + (0.6 * OPI)
    RETURN round(PACE, 2)
END FUNCTION

// Example
// EHS = 0.50, OPI = 0.80
// PACE = 0.4*0.50 + 0.6*0.80 = 0.20 + 0.48 = 0.68

Output is weighted higher than Signal (0.6 vs 0.4) so quieter collaborators are not penalized for communication style alone.

5. Trend & Anomaly Detection Algorithm

Goal: flag changes over time, not single-point scores, using a rolling baseline + deviation check (MVP version — no ML dependency; LSTM can replace the deviation step once enough history exists).

Flowchart

flowchart TD
    A[PACE/EHS/OPI history, last N periods] --> B[Compute rolling mean and std-dev baseline]
    B --> C{Current score deviates > k·σ from baseline?}
    C -- Yes --> D{Deviation persists over >=2 periods?}
    C -- No --> H[No anomaly]
    D -- Yes --> E[Classify as Persistent Deterioration]
    D -- No --> F[Classify as Sudden Change]
    E --> G[Emit Risk Signal]
    F --> G

Pseudocode

FUNCTION detect_trend_anomaly(employee_id, history, k=1.5, window=6):
    scores  = history.last(window)          // e.g. last 6 periods of PACE
    mean    = average(scores[0 : window-1])  // baseline excludes current period
    std_dev = std(scores[0 : window-1])
    current = scores[window-1]

    deviation = (mean - current) / std_dev   // positive => current is worse than baseline

    IF deviation > k:
        // check persistence across last 2 periods
        prev_deviation = (mean - scores[window-2]) / std_dev
        IF prev_deviation > k:
            RETURN {anomaly: TRUE, type: "persistent_deterioration", severity: deviation}
        ELSE:
            RETURN {anomaly: TRUE, type: "sudden_change", severity: deviation}
    ELSE:
        RETURN {anomaly: FALSE}
END FUNCTION

Complexity: O(window) per employee per run — cheap enough to run on a scheduled batch job across all employees.

6. Risk Classification Algorithm

Flowchart

flowchart TD
    A[PACE score + anomaly result] --> B{PACE >= 0.7?}
    B -- Yes --> C[Healthy]
    B -- No --> D{PACE >= 0.4?}
    D -- Yes --> E[Moderate]
    D -- No --> F[At-Risk]
    C --> G{Anomaly flagged?}
    E --> G
    F --> G
    G -- Yes --> H[Escalate one band + attach explanation]
    G -- No --> I[Keep band, attach explanation]
    H --> J[Send to Dashboard / Alerts]
    I --> J

Pseudocode

FUNCTION classify_risk(PACE, anomaly_result, features):
    IF PACE >= 0.7:
        band = "Healthy"
    ELSE IF PACE >= 0.4:
        band = "Moderate"
    ELSE:
        band = "At-Risk"

    // escalate one band if a persistent negative trend is detected,
    // even if the raw score alone still looks acceptable
    IF anomaly_result.anomaly == TRUE AND anomaly_result.type == "persistent_deterioration":
        band = escalate(band)   // Healthy -> Moderate -> At-Risk

    explanation = build_explanation(features, anomaly_result)
    // e.g. "OPI stable, EHS down 22% over 3 weeks (meeting load +40%)"

    RETURN {risk_band: band, score: PACE, explanation: explanation}
END FUNCTION

Complexity: O(1) — the classifier only reads already-computed scores; all heavy lifting happens upstream in EHS/OPI/trend steps.

Design Notes (Optimization / Responsible-AI Constraints)

  • Linear time overall: each stage (ingestion, EHS, OPI, fusion, trend, classification) processes each employee's records in a single pass — no nested loops over the full dataset, so the pipeline scales linearly with (employees × events).
  • Batchable: trend/risk classification can run as a nightly/weekly batch job rather than real time, keeping compute cost low.
  • No automatic decisions: the classifier only emits a risk band + explanation; final judgment is always routed to human review (Section 16 of the architecture doc), per the project's human-in-the-loop constraint.
  • Explainability by construction: every algorithm returns the raw contributing features alongside the score, so risk bands are never a black-box number.
